# TASK-EPIC-AUTH.md — Эпик «Регистрация и авторизация владельца»

> **Статус:** запланировано (backlog). Отдельный эпик, вынесен из MVP-скоупа `TASK.md`.
> **Источник:** issue «Добавить регистрацию и авторизацию для Владельца» (автор gastor-git).
> **Продуктовая предпосылка:** владельцев может быть несколько — каждый владелец имеет учётную запись и собственный календарь.

## Почему отдельный эпик

Фича ломает зафиксированные допущения MVP (регистрации и авторизации нет, владелец — один фиксированный профиль без учётной записи):

- `TASK.md:4-6` — «без регистрации и авторизации», «один фиксированный профиль».
- `spec/main.tsp:14-16` — `@useAuth(NoAuth)` → OpenAPI эмитит `security: [{ }]`.
- `spec/models.tsp` / `spec/operations.tsp` — сущностей аккаунта и сессии нет, все операции (включая записи владельца) публичны.
- Бэкенд: сид владельца `id=1` (`TASK.md:147`), в БД нет таблиц аккаунтов/сессий.
- Фронтенд: вход по ручному вводу `ownerId` на главной странице, понятия «логин» нет.

Ввод эпика в MVP потребовал бы пересмотра доменной модели, контракта и деплоя (появится почтовый сервис и OAuth-интеграции) — поэтому он ведётся отдельно, поверх стабильного MVP.

## Цели (in scope)

- Владелец может зарегистрироваться на главной странице приложения по имени и email.
- Подтверждение email кодом из письма перед активацией аккаунта.
- Владелец может авторизоваться по email (с кодом из письма).
- Регистрация/авторизация через GitHub и Google (OAuth 2.0).
- Несколько владельцев: у каждого свой календарь (свой `ownerId`).
- Защита операций владельца (управление графиком, событиями, список бронирований) — только для авторизованного владельца аккаунта.
- Гостевой сценарий остаётся публичным: просмотр профиля/события/слотов и бронирование без аккаунта.

## Не-цели (out of scope)

- Регистрация гостей и управление их данными.
- Пароли и их восстановление (авторизация только по email-коду и OAuth).
- Роли и права доступа, отличные от «владелец календаря».
- Управление несколькими календарями одним аккаунтом (1 аккаунт → 1 календарь).

## Продуктовая модель

| Сейчас (MVP) | После эпика |
|---|---|
| Один фиксированный владелец (сид `id=1`) | Несколько владельцев, каждый с учётной записью |
| Владелец входит по ручному `ownerId` | Владелец логинится (email-код или OAuth) и попадает в свой календарь |
| Все операции публичны | Операции владельца защищены, гостевой сценарий публичен |

Гость по-прежнему попадает на публичный календарь по ссылке `/owners/{ownerId}/events/{eventId}`.

## Доменная модель (изменения)

Новые сущности:

- **OwnerAccount** — учётная запись владельца: `id`, `ownerId`, `name`, `email`, `emailVerifiedAt`, `createdAt`.
- **OAuthIdentity** — связка аккаунта с провайдером: `id`, `accountId`, `provider` (`github`/`google`), `providerUserId`, `createdAt`.
- **Session** — активная сессия владельца: `token`, `accountId`, `createdAt`, `expiresAt`.

Существующие модели Owner/Event/Booking/Slot/Schedule не меняются по структуре; `Owner.id` больше не фиксированный сид, а привязан к аккаунту.

## API-контракт (изменения TypeSpec)

- Замена `@useAuth(NoAuth)` на security scheme с Bearer-токеном; защищённые операции помечаются `@useAuth`.
- Остаются публичными: `GET /owners/{ownerId}`, `GET /owners/{ownerId}/events`, `GET /owners/{ownerId}/events/{eventId}`, `GET .../slots`, `POST .../bookings`.
- Становятся защищёнными: `PATCH /owners/{ownerId}/schedule`, `POST /owners/{ownerId}/events`, `GET /owners/{ownerId}/bookings`.

Новые маршруты (namespace `auth`):

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/auth/register` | запрос регистрации: `name`, `email` → отправить код подтверждения |
| POST | `/api/auth/register/verify` | `email`, `code` → активация аккаунта + создание сессии |
| POST | `/api/auth/login` | запрос авторизации: `email` → отправить код |
| POST | `/api/auth/login/verify` | `email`, `code` → сессия |
| POST | `/api/auth/oauth/{provider}/start` | старт OAuth: `provider` → URL редиректа провайдера |
| POST | `/api/auth/oauth/{provider}/callback` | `provider`, `code`, `state` → создание/вход аккаунта + сессия |
| POST | `/api/auth/logout` | завершение сессии (защищён) |
| GET | `/api/auth/me` | текущий аккаунт и его `ownerId` (защищён) |

Новые модели: `OwnerAccount`, `AuthStartResponse`, `AuthCodeRequest`, `AuthSessionResponse`, `OAuthStartResponse`, `OAuthCallbackRequest`.

Новые ошибки: `401` (`UNAUTHORIZED` — нет/невалидная сессия), `403` (`FORBIDDEN` — доступ к чужому календарю), `409` (email уже занят, повторная отправка кода и т.п.).

## Бэкенд (Go)

- Миграции: таблицы `owner_accounts`, `oauth_identities`, `sessions`; `owners.account_id` (nullable) для существующего сида.
- Сид MVP сохраняется (владелец без аккаунта) либо переносится на первый зарегистрированный аккаунт — на решение (см. «Открытые решения»).
- **Email-коды:** сервис доставки по SMTP, одноразовые 6-значные коды (TTL, один активный код на email, rate-limit, повторная отправка).
- **OAuth:** клиенты GitHub/Google, `state` для защиты CSRF, `code`-обмен; связывание и логин через существующего провайдера.
- **Сессии:** генерация токена, таблица сессий с `expiresAt`, middleware-проверка Bearer-токена; защита владельческих маршрутов с проверкой `ownerId` из сессии.
- **Email/коды в тестах:** интерфейс отправителя с mock-реализацией (в тестах код читается из БД/mock, реальный SMTP в CI не требуется).

## Фронтенд (React)

- Страницы: `/login` (email-код, кнопки GitHub/Google), `/register` (имя, email), `/verify` (ввод кода).
- Хранение токена и клиентские заголовки авторизации в API-клиенте (`src/lib/api.ts`).
- Защита маршрутов владельца; на главной `/` вместо ввода `ownerId` — кнопки «Войти»/«Зарегистрироваться»; авторизованный владелец попадает на свой `/owners/{ownerId}`.
- Кнопки OAuth, обработка callback-редиректа с провайдера, выход, отображение `401/403` с переходом на логин.

## Инфраструктура

- `.env.example` и `docker-compose.yml`: `SMTP_HOST/PORT/USER/PASS/FROM`, `APP_BASE_URL`, `GITHUB_CLIENT_ID/SECRET`, `GOOGLE_CLIENT_ID/SECRET`, `SESSION_TTL`.
- Почтовый сервис: в проекте его нет — подключается внешний SMTP (на время разработки допустим mailpit/dev-контейнер).
- E2E (Playwright): сценарии регистрации/входа/выхода/ошибки кода и защиты владельческих страниц — с mock-доставкой кода.

## Открытые решения (дефолты)

- **Авторизация по email — это код из письма, а не пароль** (соответствует формулировке issue). Пароли и их восстановление не храним.
- **Сессии:** токен в `httpOnly` cookie (`Secure`, `SameSite=Lax`) — рекомендованный дефолт; альтернатива — `Authorization: Bearer` (проще для API-клиента, хуже для XSS).
- **Один аккаунт ↔ один календарь.** У аккаунта может быть несколько `OAuthIdentity` (вход через GitHub или Google — один и тот же аккаунт по email).
- **Судьба сида `id=1`:** либо остаётся как публичный демо-профиль без аккаунта, либо мигрирует на первый зарегистрированный аккаунт. Защищённые операции сида в любом случае закрываются.
- **Код подтверждения:** 6 цифр, TTL 10 минут, один активный код на email, лимит на отправку.
- **Email-доставка:** интерфейс `MailSender` с mock в тестах; на проде — внешний SMTP. Отдельный почтовый сервис в репозиторий не добавляем.
